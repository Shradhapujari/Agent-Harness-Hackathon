1. The Problem We Solve

🔥 Alarm storms in data centers

When one thing breaks in a data center — a CRAC cooling unit, a power feed, a hung server — it does not produce one alert. It produces a cascade: temperature sensors trip, PSU stress alarms fire, a dozen nodes drop off Kubernetes, pods crash, applications error out. Each monitoring layer fires independently. A NOC engineer wakes up to 40+ alarms that are really 1 root cause, and must manually correlate them across tools (BMC/Redfish, Kubernetes, Prometheus, NetBox) under time pressure.

Why this is a proven, funded problem

  • BigPanda — raised $350M+; entire product is alert correlation & triage. Customers: UBS, London Stock Exchange, IHG, Paramount.
  • Moogsoft — AIOps alert-correlation pioneer, acquired by Dynatrace (2023).
  • PagerDuty, OpsRamp, Shoreline.io, Keep — all monetize alert noise → triage.
  • Alert fatigue is a documented driver of missed incidents and on-call burnout.

🎯 Our angle: the missing execution loop

BigPanda & co stop at enriched incidents + recommendations. A human still performs every action: drains the node, checks the BMC, power-cycles the server. We close the loop. Our agent doesn't just say "probably the CRAC in rack R4" — it proposes, requests approval for anything destructive, executes via real APIs (Redfish / Kubernetes), and verifies recovery.

2. What We Are Building

DC-Sentinel: an autonomous triager-operator agent that ingests a live alarm stream, correlates it down to a root cause, gathers evidence across three layers of the data center, proposes ranked remediation actions, and executes them — with a human approval gate for anything irreversible.

The flow (one incident, end to end)

🧨 Chaos injector fires CRAC-failure scenario→ 40 alarms land in Alertmanager→ 🤖 Triager agent ingests→ Subagents: correlate / classify / enrich→ 1 root cause + noise marked→ Ranked actions proposed→ 👤 Approval gate→ Execute (drain / power-cycle)→ ✅ Verify recovery + incident report

Worked example (the demo script)

  1. Inject: rack R4 CRAC unit "fails". Thermal alarms ×3 fire, then PSU stress, then 12 node-down alerts, then pod errors — a realistic cascade.
  2. Correlate: subagents group the 40 alerts by device/rack/time-window → one cluster in rack R4; rest flapping noise.
  3. Enrich: Redfish shows inlet temps 38°C → 47°C on R4 nodes; NetBox shows R4 = 12 compute nodes, 3 tenants affected.
  4. Decide: drain + reschedule pods to cooler racks Auto; graceful shutdown of R4 nodes to prevent thermal damage Approval.
  5. Execute & verify: pods rescheduled, node temps fall, alarms clear, incident report generated with full evidence chain.

Why a custom mock BMC instead of DMTF's stock mockups?

  • DMTF Redfish-Mockup-Server is static JSON — temps never move, power-cycle does nothing. Useless for a live demo.
  • Our mock has a state loop: fake load drives CPU temp up, fans respond, wattage follows — and a chaos endpoint to inject thermal spikes, PSU failure, hung hosts, SEL entries.
  • We control the drama → deterministic, repeatable demo for judges.

Why Ignition SCADA was considered but skipped

Ignition Maker Edition is free and has simulator drivers + tag alarms, but demands ~half a day of Gateway/config learning — too risky in a one-day hack. The alarm-bus pattern (Alertmanager) is the industry-standard intake format anyway, and keeps the focus on agent logic, not SCADA plumbing.

6. Glossary for Newcomers

  • BMC (Baseboard Management Controller): chip on a server motherboard that runs independently of the OS — control power and read sensors even when the machine is off or hung. Accessed via Redfish.
  • Redfish: DMTF industry-standard REST/JSON API for server hardware management (power on/off, temps, fans, event logs).
  • SEL (System Event Log): hardware error log readable from the BMC — DIMM errors, PSU faults, thermal trips.
  • kind: runs a real Kubernetes cluster inside Docker containers — used for local testing and demos.
  • MCP (Model Context Protocol): standard way for agents to connect to external tools/APIs — the harness speaks it natively.
  • Alertmanager: the de-facto standard alert-routing service in the Prometheus ecosystem; alarms land there as JSON.
  • NetBox: open-source data center inventory (racks, devices, tenants) — source of truth for "what is affected".
  • Alert storm / fatigue: one failure → hundreds of alerts → humans stop trusting or noticing them.
  • Triage: turning a pile of raw alarms into "here is the root cause, here is the blast radius, here is what to do."
  • Approval gate: agent must pause and get a human "yes" before any irreversible action (power-off, reboot, delete).
